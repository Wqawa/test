## 修：切回加密包后关窗口不清理（51f05cf1）

现象：加密包 A → 切到普通 mod B（清理屏跑过）→ 切回 A → 手动关窗口**不出清理屏**，直接退出；
再从 A 切到别的 mod 又会出清理屏。

根因：`ModPackCrypto.needsCleanup()` 第一行 `if (cleanupDone) return false;`。`cleanupDone` 是
清理屏自己的进度闩锁（一次擦除结束置 true，只有 `beginCleanup()` 会清），A 重新解密只把
`sessionDecrypted = true`，闩锁还是上一轮的 true → 关窗时的 veto 拿到“不需要清理” → 直接退。
切 mod 那条路（`beginSwitchCleanup`）压根不看这个标志，所以照常触发。
退出钩子仍会 `releaseZips()` + `cleanCache()`，所以没泄露，只是没跑也没显示那屏。

修法：把这行从 `needsCleanup()` 删掉。一轮擦除之后 `sessionDecrypted` 已是 false、`releaseZips()`
也把 `loadedZips` 换成空 Map，两个真实信号本来就返回 false，闩锁纯属多余且会过期。
受益的还有 `SaveWarning.exitGame()`（编辑器有暂存改动时关窗口走同一个判断）。

构建通过，exe 11:39。教训：**「某次操作已完成」的闩锁不要参与「现在需不需要做」的查询**。

## 彩蛋 25% + 转场旋转（75565b76、4242da2f）

- `ModPackLoadingState.EASTER_EGG_CHANCE` 20→4（`FlxG.random.int(1,4)==1`，25%）。
- `MusicBeatTransition`（官方文件，但 tile 转场是 fork 在 7060c7bf 新加的）：原来
  `angle = 45 * (1 - scaleFactor)`，即瓷砖从 45°（菱形）长成 0°（方）；现在
  `tileStartAngle + (tileEndAngle - tileStartAngle) * scaleFactor`，`tileEndAngle=90`。
  起始角从 `tileStartAngles = [0, 180]` **每次转场抽一次**（不是每块砖，逐砖随机看着像噪点）。
- 关键结论（一开始我算错了，用 PIL 渲染对照才纠正）：正方形的对称性是 90° 倍数，
  所以 `0→90` 和 `180→90` **不是**同一张图——同一进度下瓷砖倾向 ±22.5°，只有正中间
  （s=0.5，两者都是菱形）重合。像素对照：22.5° vs 157.5° 有 574 px 最大差 255；
  45° vs 135° 只差 AA 噪声（最大 24），那才是真正等价的一对。
  推论：**判断两个旋转是否等价，要看角度差是不是 90 的倍数，不是看方向反没反**。
- 90° 收尾是安全的：正方形转 90° 与 0° 像素等价，且 flixel 的矩阵在 90° 时 cos≈6e-17，
  取整不会开缝。

## 修：清理屏点“继续”没反应（23ab82a9）

现象：加密包 A → 切到“disable mod（列表末尾那个 null 项）” → 清理屏跑完、倒计时结束、
按钮能点，但永远不动。

根因：`ModSwitchMenu` 的列表 `mods.push(null)`，所以 **null 是合法目标**；而
`ModPackCrypto.queuedSwitch` 用 null 同时表示“没排队”。`beginSwitchCleanup(null)` 存了个 null，
`completeSwitchCleanup()` 读回来 `if (target == null) return;` 直接返回，state 没切；而
`ModPackCleanupState.finish()` 在调用前已经把 `quitting = true`，于是之后每次点击/倒计时都空转。
按钮能按正是这个状态的症状。

修法：加 `switchQueued:Bool` 单独表示“有没有排队”，`queuedSwitch` 只管值；`completeSwitchCleanup()`
返回 Bool，清理屏拿不到续接时 `FlxG.switchState(new MainState())` + 一行 warn，而不是干等。

顺带确认：中途“自己切自己”不参与——`target == currentModFolder` 在入队前就返回了。卡死完全由 null 目标决定。
教训：**用 null 兼作“没有”和“值就是 null”的哨兵，迟早炸在一条真实路径上**。

## 修：暂停时关窗口，未保存提示顶掉暂停菜单（5b5b8c4d）

现象：编辑器里有未保存改动 → 从编辑器进歌 → 暂停 → 关窗口 → 弹“Unsaved Changes!” →
点 Cancel 后歌继续跑，暂停没了。

根因：`SaveWarning.triggerWarning()` 里是 `FlxG.state.openSubState(...)`。暂停时 `FlxG.state`
仍是 PlayState，而 `FlxState.openSubState()` 会**销毁已有的 subState** 再装新的 —— 暂停菜单就是被
它销毁的。提示关掉后 `subState = null`，PlayState 就恢复 update，等于取消暂停。

修法：沿 `host.subState` 一路往下找到最深的一层再 `openSubState`（和 `UIState.openContextMenu`
同一个走法）。暂停菜单留在下面，`UIWarningSubstate.onSubstateOpen` 会把它的
`persistentUpdate = false`（冻结但继续绘制），Cancel 后回到暂停菜单。

坑的通用性：**任何“X 状态下弹窗”都必须挂在最深 subState 上**，否则会静默销毁当前菜单。
`FlxState.openSubState` 没有“叠加”语义，flixel 的 substate 是一次一个。

## 修：提示里点“保存”不合并进 zip（814aafe5）

现象（承接上一条）：编辑器有未保存改动 → 试玩进歌 → 暂停 → 关窗口 → 点“Save & Exit Game”，
`.cne/mods/<mod>/` 里有文件，但压缩包没被改写。下次启动靠 overlay 读暂存目录，看着像保存了。

根因：`SaveWarning` 的“保存”按钮执行的是 `saveFunc`，而 `saveFunc` 归装它的那一方：
编辑器装的只写暂存目录（编辑器里合并留给“下次关闭”）；`ZipEditCache` 装的才是合并。
试玩时 `PlayState.chartingMode` 装的是 `Charter.saveEverything(false)`，写完后
`exitGame()` 直接 `System.exit` —— 没有“下次关闭”，合并永远不发生。

修法：`exitGame(saved:Bool)`。保存路径传 true，先 `ZipEditCache.pendingMod()`（此时
`preventClosing` 还开着，窗口不能中途消失），有暂存就切 `ModPackMergeState`（异步、带进度），
回调再 `exitGame(false)` 走清理屏/退出；“Exit Game”传 false（用户选择不合并，留到以后）。
顺序上合并必须在清理屏之前，包要是完整的。

通用教训：**“保存到暂存区”和“合并进容器”是两步，任何以结束进程收尾的路径都必须自己补第二步**。

## 修：歌曲内退出到菜单弹旧版提示 + 保存不进 zip（685bc1cb / 0632d0b1 / c8ec0f9d）

1. **旧版提示**：`PlayState` 的 chartingMode 里设了 `SaveWarning.warningFunc = saveWarn`。上游
   `triggerWarning` 是“先调用 hook，再看 state 是不是 UIState 决定要不要再开通用对话框”——上游在
   PlayState 里只会有旧对话框；本 fork 为了标题栏关窗口能提示，放开了 UIState 限制，于是两个对话框
   同时出现。修法：去掉 hook，`saveWarn` 直接转调 `triggerWarning`。`PlaytestingWarningSubstate`
   留在树里（上游文件、脚本可能 import），但没人调用。

2. **提示能连开、也能被绕过**：`WindowUtils` 的规则是“第二次关窗口就放行”（__triedClosing）。
   提示开着时再点 X 会直接退出。现加了两道：`triggerWarning` 里若最深的 substate 已经是
   `UIWarningSubstate` 就 return（不叠加）；`SaveWarning.init` 注册一个 close veto，
   `showWarning` 为真时一直挡住关窗。

3. **普通 zip 合并不进去（真 bug）**：未加密 `.zip` 由 `ZipFolderLibrary` 用 `SysZip` 常开句柄读；
   `replaceWith` 用 rename 换包，Windows 拒绝 rename 被打开的文件（实测 `Permission denied`）。
   于是这类 mod 的合并**从来没成功过**，只在日志里留一句 could not merge。修法：合并前列出
   `Paths.assetsTree.libraries` 里读这个包的 `ZipFolderLibrary`，`releaseForReplace()` 松手，
   swap 完 `reopenAfterReplace()`（重开句柄 + 重建 assets/lowerCaseAssets/nameMap，整体赋值避免读到半张表）。

4. **试过又撤回**：让“保存并退出到菜单”当场合并（keepStaged 保留暂存文件）。不行——运行中的 mod
   资源库读的是旧包/旧解密副本，重写后它们指向的字节已经不存在；保留暂存文件只掩盖了刚保存的那几个文件。
   合并只能在“这个 mod 不再被用”时做：关游戏、切 mod。这条写进了 docs/RE-ENCRYPTION.md。

教训：**zip 包的“保存”和“合并”是两步；合并的安全点只有进程结束或整包重载**。
