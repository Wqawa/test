## 启动加速：先量后改（commit e24a66e9 / 7c561325 / b6a895ad）

- 基准（8 MB、neko、纯 Haxe）：ChaCha20 全量 6156 ms，HMAC-Sha256 全量 33072 ms，
  64 KB 切片解密 98 ms。**HMAC 比全量解密贵 5.4 倍**，所以"惰性解密"只省 1/5 左右；
  neko 绝对值不能外推到 hxcpp，只采信比例。基准脚本在 `.workbuddy/bench/`（已 gitignore）。
- 真正的浪费：wrapped 模式（`Options.wrapDecryptedPacks` 默认 true）先把整包解出来，
  再用随机会话密钥全文 XOR 一遍——第二次全量运算对保密性毫无增益，因为容器密文本来就是密文。
- 改法：`ModPackCrypto.openEncrypted()` 只校验 HMAC 就返回密文 + 派生密钥；
  `ProtectedBuffer.fromCipher()` / `SysZip.fromCipher()` 读取时用包自己的 keystream 按偏移解密。
  结果：CNEZ 包从 2 次全量 ChaCha20 降到 0 次，内存里始终是密文，包大小的明文缓冲消失。
  AES 密码 zip 仍走原来的 `readableCopyBytes` + 包裹。
- 编辑器：Mod Pack 页多选（原来只取 `files[0]`，脚本页早就多选了）+ 队列串行跑，
  批量时输出到源文件旁边（`_encrypted` / `_password` / `_decrypted`），单个仍弹另存为。
  新增 `ModPackSelfTest.hx` 覆盖 CNEZ 布局/往返/错密钥/篡改/惰性读取，接进 Tools 菜单。
- 文档：新建 `docs/ARCHITECTURE.md`（36 新增文件分 6 组、18 个接缝点带行号、启动调用链、
  磁盘/内存生命周期、29 个未审计文件的说明），AGENTS.md 文档地图加一行，RE-ENCRYPTION.md §2.2 同步。
- 编译：`-D no-compilation` 18 秒抓语法错（第一次就抓到"类内 typedef"不合法）；

## v2 容器：分块 tag（commit 9d9d21d9 / 907e6cd5）

- 用户确认走"路径 3"。设计：48 字节头（magic/ver/salt/nonce/len/chunkSize/count）+ 块表
  （count × 32B）+ 根 tag（覆盖头+块表）+ 密文。`pack()` 默认出 v2，`packV1()` 保留旧布局，
  `openEncrypted()` 按版本字节分派——**旧包不用重新打包**。
- 实测（2.5 MB、neko、`.workbuddy/bench/V2Test.hx`）：v2 打开 **1 ms**，v1 要做的全量
  HMAC **7964 ms**。但收益有边界：建 zip 索引要读末尾/中央目录/各 local header，那些块会在
  索引时被校验，条目分散就越接近全量——文档里写明了，不许只吹 open 那 1 ms。
- 安全取舍（写进 RE-ENCRYPTION.md）：v1 打开就发现任何篡改；v2 要等含那块的数据被读。
  块表由根 tag 保护改不了；读到坏块后 `ProtectedBuffer.integrityFailed` 置位、后续读返回空，
  不把坏数据交给解码器。
- **自己复查抓到的真 bug**：chunk 解密的 counter = `1 + start/64`，要求 chunkSize 是 64 的倍数，
  否则第二个块起全部错位。已在 `CnezV2.open` 加 `chunkSize % 64 != 0` 拒绝。
- 踩坑（第二次）：Haxe **不允许类内 typedef**。`CnezV2.Opened` 和 `ModPackCrypto.OpenedPack`
  都得挪到模块级；跨模块引用同包 typedef 要写全名 `ModPackCrypto.OpenedPack`。
- 验证方式：编辑器自检只能在 GUI 里跑，所以另建了 `.workbuddy/bench/`（fake ScriptCrypto +
  CnezV2 副本 + V2Test），2.5 MB 跨 3 块跑 14 项断言全过——含"每块用自己的 counter 解密"
  和"块内非对齐读取"。**编译通过不等于格式正确，这条以后照做**。
- 编译：类型检查 4 轮才过（typedef × 2、inline var 数组常量 × 1），全量 2 分 36 秒。

## v2 回归：v2 包"解密不了"（commit 373bc397）

- 用户实测报"解密不了了"。根因：`ModPackCrypto.keyWorksUncached` 判断密钥是否可用时，
  读偏移 40 处的 4 字节当密文解密看是不是 `PK`——那是 **v1 的 payload 起点**；v2 的偏移 40
  是 `chunkSize` 字段，于是所有密钥都判定为错 → `resolveKey` 返回 null → 加载器直接放弃该包。
- 修复：新增 `CnezV2.verifyKeyFile(path, pass)`，读「头部 + 块表 + 根 tag」（几 KB）校验根 tag，
  比 4 字节探测更强；`keyWorksUncached` 按版本字节分派。
- **教训（重要）**：改磁盘格式时，必须 grep 所有"按固定偏移读容器"的地方，不能只改
  open/unpack 这条主路径。这类 bug 编译能过、编辑器自检也能过（自检不覆盖文件探测路径），
  只有真机加载才暴露。事后 grep 了 `HEADER_SIZE` / `get(4)` 确认无其它遗漏。
- 验证：`.workbuddy/bench/V2Test.hx` 加了三项真实文件断言（对/错/文件不存在），17 项全过。
- 另：`failedPacks` 是进程内 Map，加载失败过的包在同一次运行里不会重试，用户需重启游戏再试。

  `SysZip.closeHandle()` + `ModPackCrypto.releaseFileHandle()`，`ZipEditCache.replaceWith` 开头调用。

  退出钩子仍会擦内存缓冲和密钥文件，只是没有进度屏。两条关闭路径都改用它：
  `Main.installModCleanupVeto`、`ModPackCrypto.installCloseVeto`。

## 脚本清单校验 + Standard 模式补漏（commit 031b2990 / 66652a7b）

- 标记升级到 **v2**：一个文件装下 salt / 密码摘要 / `scripts N` + 每行 `<sha256> <path>`。
  `parse` 同时接受 v1（无清单 → 不校验）和 v2。
- 打包时 `collectScripts()` 用 `haxe.zip.Reader` 全量解压收集 `.hx/.hxs/.hxb` 的哈希，
  只保留 `scripts/` 之后的路径（和 `ScriptGuard.normalize` 对齐）。
  **注意：放在 scripts/ 以外的脚本不会进清单，运行时会当作"多出来"拒掉。**
- 运行时 `ScriptGuard` 在 `HScript` 两处拦截：容器分支（`ScriptContainer.unpack` 前）和
  明文分支（`Assets.getText` 后）。被拒脚本 `code = ""` 占位，不执行。
  违规汇总到 `violations`，`MainMenuState.reportRefusedScripts()` 弹红窗，一次运行一次。
- **Standard（AES 密码 zip）也能带标记**：之前 `packProtectPass()` 见 `currentPackMode == 1`
  直接返回 null 是漏的。现在 `encryptZip` 从路径读，所以流程是
  读源 zip → ZipInject 注入标记 → 写 `.cne/temp/protect_pack.zip` → 加密 → 删除（成败都删）。
  运行时不用改：`needsKey()` 对 AES 包返回 true，照样走内存解密 → `applyFromPack` 能读到。
